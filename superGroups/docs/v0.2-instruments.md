# superGroups v0.2 — custom instruments and MIDI-conditioned audio

Status: staged design and implementation backlog, 2026-09-08. No new audio training or changes to the live player are included in this milestone. The existing musician checkpoints remain the note-generating layer.

## Decision

Separate **who plays** from **what they sound like**. A musician generates the performance; an instrument renders it. The same trancefusion guitarist can play a clean electric guitar, an acoustic instrument, or a custom learned timbre without retraining its musical decisions.

Pipeline:

```text
musician model → MIDI + expression → chosen instrument renderer
             → aligned PCM stems → existing mixer → WAV / MP3 export
```

Generate waveform samples, not MP3 file bytes. MP3 is the final lossy delivery format. Preserve lossless stems for mixing and repeat rendering. Lossy codec delay and padding must not become a source of inter-track timing errors.

MIDI-conditioned neural synthesis is demonstrated by [MIDI-DDSP](https://arxiv.org/abs/2112.09312). Its hierarchical separation of note/expression decisions and sound generation is a useful design reference. The [reference implementation](https://github.com/magenta/midi-ddsp) uses TensorFlow and is archived; it is research evidence, not a drop-in maintained PyTorch dependency. Its published pretrained instrument set does not include guitar. We will retain PyTorch for our own prototype rather than assume the reference checkpoint can supply our guitarist's sound.

## Release sequence

### 0.2a: instrument interface and sampled baseline

- Add an instrument choice separate from the musician choice on each mixer channel.
- Implement a renderer boundary around the existing simple synthesizer.
- Add one custom sample instrument using pitch/velocity mappings and release handling. This establishes a realistic-sounding baseline without an audio model training requirement.
- Render each track to an independently mixable lossless stem with a common sample clock.
- Compare the identical MIDI played by the current synthesizer and the sampled instrument. Keep performances unchanged so timbre comparisons are meaningful.
- Add WAV and MP3 mix export. MIDI remains available separately.

### 0.2b: monophonic neural guitar pilot

- Train a compact PyTorch DDSP-style renderer: a network predicts harmonic amplitudes, a noise envelope, and a loudness envelope that drive differentiable synthesis.
- Condition explicitly on note pitch, onset, note-off, velocity, and instrument identity. Expressive controls are separate optional inputs, not permission to change the score.
- Model attacks and release noise; compare a learned transient/residual path only if the simpler system misses guitar attacks.
- Begin with one guitar, one recording setup, and monophonic phrases. Chords, strumming, multiple strings, and full-band audio are later work.
- Treat T4 operation as a benchmark target, not a verified memory/runtime promise. Begin with short clips, small batches and mixed precision; record peak memory, throughput, and audio quality before setting a training budget.
- Render offline in Colab first. Deliver cached stems to the existing static webapp. No GPU service or browser neural inference is required for the pilot.

[DDSP](https://magenta.tensorflow.org/ddsp) combines learned controls with differentiable oscillators, filters, and reverberation. Its structural assumptions motivate this pilot over training a large unconstrained waveform generator from scratch. This is an engineering choice for the next experiment, not a claim that DDSP will necessarily outperform a good sampler on guitar.

### Later: expressive and polyphonic instruments

- Extend the musical performance representation beyond the present sixteenth-note grid and eight velocity bins.
- Preserve precise onset/offset times, pitch bends, continuous expression and articulation controls. MIDI by itself does not uniquely describe a performance's timbre or physical technique.
- Add string/fret, legato/slide, palm-mute, vibrato, and pick-position annotations only when recordings and renderer support them.
- Evaluate polyphonic rendering with shared effects, rather than assuming independently summed monophonic voices reproduce strumming or amplifier interaction.
- Consider a MIDI-conditioned latent audio model for richer texture if the pilot exposes a quality ceiling. It must pass note/timing fidelity tests; plausible sound alone is insufficient.

## Proposed integration contract

This is an interface sketch, not an implemented API:

```python
stem = renderer.render(
    performance=performance,       # source MIDI plus optional expression
    instrument_id=instrument_id, # independent of musician_id
    sample_rate=sample_rate,
    seed=seed,
)
```

The performance includes canonical timing in seconds, tempo changes, notes, velocity, and optional expressive controls. Do not re-quantize MIDI imported for rendering to the current training grid.

Every result includes PCM audio, sample rate, sample count, release-tail duration, instrument/checkpoint version, input performance hash, and rendering seed. All stems begin at the same origin and retain leading silence. Mix them at one sample rate; encode only the final mix for MP3 download.

Instrument manifests distinguish `simple_synth`, `sample_bank`, and `neural` backends; declare pitch range, supported articulations, polyphony and asset/checkpoint version. Unsupported input must produce an explicit error or an identified fallback. Do not silently discard bends, notes or overlapping voices.

Musician and instrument checkpoints are independently versioned. The 13 current musician choices and their existing saved performances remain usable. A guitar timbre change is not a new musician identity.

## Data needed before audio training

The existing synthetic MIDI exercises teach note choices; they contain no real guitar sound to learn. Start with clean, isolated recordings we can use, preferably dry direct-input recordings, with known note timing/pitch/velocity or carefully checked transcriptions. Include attacks, full decays, repeated notes, multiple dynamics, and connected phrases across the intended range.

The [DDSP-VST training guide](https://github.com/magenta/ddsp-vst/blob/main/docs/getting-started.md) describes a 10–20 minute monophonic recording workflow. That is evidence that small-data experiments are possible, not a guarantee of realistic guitar quality or sufficient coverage for our instrument. Start with a coverage audit rather than a fixed promise about minutes of data.

Split by recording session or performance before slicing clips. Hold out complete phrases, pitch/dynamic combinations, and repeated takes. Preserve original audio, alignment, recording metadata and model-ready derivatives. Avoid training from a full-band mix for the first instrument; separation artifacts and other instruments would contaminate the target.

## Evaluation and acceptance gates

Use exactly the same held-out MIDI for simple-synth, sampler and neural renderers. Evaluate the neural pilot before committing to broad instrument training.

1. **MIDI fidelity:** test isolated notes, gaps, repeated notes, long holds, velocities, pitch changes and supported expressive controls. Measure pitch, onset/offset timing, omitted/extra notes and release behavior. A model must not earn a good score by producing silence. Set tolerances from the baseline and perceptual requirements before evaluating the candidate.
2. **Sound quality:** blind listening comparisons plus spectral/attack/decay diagnostics. Pitch correctness alone is not realism. Document where the sampler remains better.
3. **Generalization:** unseen phrases and held-out recording material, not random clips from the same take used in training.
4. **Mixer correctness:** common clock, intact leading silence, independent gain/mute/solo, aligned rendered length and repeatable export. No per-stem normalization that erases learned dynamics.
5. **Compute:** actual T4 memory, training cost, and seconds of rendering per second of audio. Measure before choosing real-time deployment.
